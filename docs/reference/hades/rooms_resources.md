# Hades I resources, gathering, rooms and rewards

This is the source-backed capability map for [#572](https://github.com/TeaganRicardo/MacGamingTrainer/issues/572). The supported image is owned by `Backend/games/hades/module.json.supportedBuild`. `world_catalog.json.sourceEvidence` binds the native script and official bilingual text inputs; `Tools/generate_hades_world_catalog.py --content <Content>` reproduces that registry without executing game scripts. Combat and boon effects have their own [map](combat_effects.md); [management parity](management-parity.md) records [#573](https://github.com/TeaganRicardo/MacGamingTrainer/issues/573), with semantic Save Editor completion retained in [#584](https://github.com/TeaganRicardo/MacGamingTrainer/issues/584).

## Native capability and delivered behavior

| Hades concept | Native owner | Trainer outcome and boundary |
| --- | --- | --- |
| Permanent resource values | `RoomManager.lua:AddResource`; `GameState.Resources`; `GameState.LifetimeResourcesGained` | The seven existing direct editor rows remain absolute edits. The separate Gain Resources action calls `AddResource` with a positive integer, retaining lifetime totals, native `OnAddedFunctionName` effects and native resource UI. It does not substitute an absolute assignment. |
| Obol gain | `RoomManager.lua:AddMoney` | The gain action calls `AddMoney`, preserving `MoneyRecord`, lifetime totals, native UI and `BlockMoney` effects. An existing native effect may block the gain. |
| Fishing point generation | `RoomManager.lua:IsFishingEligible` and the fishing branch of `HandleSecretSpawns` | Activates one existing inactive map fishing point after native eligibility succeeds with the random chance forced locally. It preserves the fishing unlock, minimum-room spacing and persistent completed-fishing history; records `ForceFishing`, trait use and `LastFishingPointDepth`. An existing or completed fishing point prevents another generation in that room. |
| Fishing, catches and turn-in | `FishingScripts.lua:StartFishing`, `GetFish`, `RecordFish`, `TurnInFish`; `RoomPresentation.lua:FishingEndPresentation` | Fishing remains the native interactive minigame, catch selection, codex/objective progress, held/total catch records and turn-in rewards. Generating a point does not claim a catch or replay the minigame. There is no flora, mining or garden owner analogous to Hades II in this native collection family. |
| God, Hammer, Pom and Chaos reward objects | `RunManager.lua:ChooseLoot`; `RoomManager.lua:GiveLoot`, `CreateWeaponLoot`, `CreateStackLoot`, `CreateLoot`; `LootData.lua` | Generates the selected canonical native reward near the current hero. Native loot-source requirements are checked. Ordinary god/Chaos objects use `GiveLoot`; Hammer and Pom use their native dedicated creators. Native menus, trait options, rarity rules and selection remain native. Giving loot retains native forced-boon use consumption. This generates an object; it does not directly acquire a chosen boon. |
| Resource, health and Obol pickups | `Interactables.lua:CreateConsumableItem`, `ApplyConsumableItemResourceMultiplier`; native reward construction in `RoomManager.lua` | Generates the selected canonical consumable at zero purchase cost, applies native room/reward multipliers, extracts native property values and registers it in `ActivatedObjects`. Collection and resulting health/resource bookkeeping remain native. It does not mark the pickup collected or clear a combat encounter. |
| Selected next-door reward | `RunManager.lua:IsRoomRewardEligible`, `RewardStoreData` in `LootData.lua`, `SetupRoomReward`; `RoomManager.lua:AssignRoomToExitDoor` | Replaces the selected ready ordinary exit's target-room reward with an eligible native reward descriptor. Native descriptor requirements and overrides are preserved, including Hammer/Hermes/Pom gating and native room reward exclusions. Fixed/first-fixed/no/deferred-reward targets and potentially forced target rooms are unavailable. Chaos loot has a native direct-generation path; it is not an ordinary door reward. |
| Combat, character, shop, fountain and miniboss routes | `RunManager.lua:IsRoomEligible`, `IsRoomForced`, `ChooseNextRoomData`, `CreateRoom`; biome `RoomData*.lua` | Selects a currently eligible room of the requested native category only when no eligible native candidate could currently be forced, constructs it with the native owner, then assigns it to the selected ready ordinary exit. Force checks include candidates outside the Trainer's categories, such as Tartarus depth-11 `A_PreBoss01`. Linked/next-biome flows remain protected. Room creation updates native creation counts; restoring a door does not falsify those counts. |
| Story character interactions | Native `_Story` room definitions, their requirements and native room events | A character route leads to an eligible native story room. The game creates its character, dialogue, gift and reward interactions when the player enters normally. The Trainer does not fabricate unlock history, select arbitrary dialogue or claim an immediate NPC spawn. |
| Thanatos encounter | `EncounterSets.lua:ThanatosEncounters`; `RunManager.lua:IsEncounterEligible`, `ChooseEncounter`, `SetupEncounter`; `RoomManager.lua:LeaveRoom`, `RecordEncounter` | Schedules one eligible Thanatos encounter for the selected exit's future room. The `ChooseEncounter` hook consumes it once at the native selection point and rechecks eligibility. Native `LeaveRoom` still records the encounter and performs the real transition. UI feedback says scheduled; it does not report that the encounter has occurred. If eligibility changes, the normal native encounter selector runs. |
| Chaos Gate | Shared secret-point pool in `RoomManager.lua:HandleSecretSpawns`; `IsSecretDoorEligible`, `GetSecretDoorCost`, `ChooseNextRoomData`, `CreateRoom`, `AssignRoomToExitDoor` | Creates one native secret door at an available map entrance point while preserving native eligibility, cost, secret-room creation, used-presentation owner, trait use and last-depth bookkeeping. Existing Chaos and Erebus gate footprints reserve their nearest native secret points through `GetClosest`; a locked gate reserves its point as well. Availability and generation use that same filtered pool. Ready exits get the native unlock presentation. Entry still requires the player's native interaction and health cost. An existing Chaos Gate prevents another generation. |
| Infernal Trove, Well of Charon, Pool of Purging | `RoomManager.lua:HandleSecretSpawns`, `IsChallengeSwitchEligible`, `IsWellShopEligible`, `IsSellTraitShopEligible`; `SellTraitScripts.lua:GenerateSellTraitShop`; `ObstacleData.lua` | Creates one selected native chamber object on a free map pedestal. The synchronous native spawn owner constructs its encounter, requirements, cost/value/options, obstacle and depth records. Eligibility hooks suppress unrelated object generation only during this call; chance flags are restored even on failure. Used pedestals and existing owners are excluded. Ready rooms receive the native usable state, prompt and unlocked animation. Trove activation, purchases and boon selling remain native interactions. |
| Erebus/Pact gate and special event-only rooms | Shrine-point-door native branch and requirement owners; linked/next-set/forced room data | These Hades concepts exist and keep their native Pact, challenge, story and biome rules. This change adds no Trainer command to manufacture them or force their event outcomes. The scoped chamber-object operation explicitly suppresses these unrelated branches. |

Native chance forcing is scoped to the requested operation. Native eligibility requirements remain authoritative; the UI lists only eligible routes and chamber objects and disables fishing/gate generation when unavailable. A selected reward that fails its native source or descriptor requirements returns the localized unavailable result before mutation.

`RunManager.lua:ChooseNextRoomData` gives its eligible forced pool priority over ordinary eligible rooms. `IsRoomForced` can itself draw `RandomChance` for depth windows and remaining-wing rules. Trainer inspection calls that native owner with the current run, source room, candidate and ordinary-selection arguments, while temporarily treating positive force chances as possible. The exact original callback is restored after success or error. This deliberately protects potentially forced routes; it is not a receipt of an earlier native random selection. Status, disabled inspection and route availability do not redraw force chances, and the ordinary native selector retains its original RNG calls. The fixed depth-11 pre-boss rule follows native `ForceAtBiomeDepthMin/Max`; `ForcedFirstReward` also protects its shop reward.

## One-shot ownership and recovery

The adapter and debugger worker both validate the canonical command payload. World commands are explicit one-shots and never enter `DEFAULT_PREFERENCES`, connection configuration or a profile. Resource gain carries the existing hero token. Object and door commands additionally carry an opaque room token containing resident generation, run identity and native room identity. Door tokens contain the native door and target-room identities and the currently observed reward identity. Native in-place door rerolls invalidate old tokens and remove stale restore authority.

Door edits replace the actual `door.Room` graph and refresh `CurrentRoom.OfferedRewards`, the native use prompt and preview. Old preview object IDs are removed before native preview recreation. The player uses that door normally; `LeaveRoom` owns encounter recording, room-history updates, shop generation, checkpoint and `LoadMap`. The command never calls yielding `LeaveRoom` or a native menu inside a debugger-side protected transaction.

Restore Original Exit is available only while the live door still owns the applied target and reward signature. It restores that door's original native target reference and preview; it does not replay room creation or undo native resource/encounter records. A native reroll or target replacement invalidates this restore lease. The sibling combat reroll-permission lease is keyed to the actual target room so it cannot restore a stale flag after a room replacement.

A scheduled Thanatos intent is held only in the resident factory, bound to run, hero, original source room and future-room object. It is consumed before encounter setup. Changing only that door's reward preserves the pending encounter; replacing the route, restoring the exit, leaving its source room, changing hero/run, Disable All or resident replacement cancels it. Native saves and profiles cannot resurrect it. Committed gain, spawned native objects and applied door edits are one-shot results; Disable All does not fabricate inverse gains or erase those native results.

The synchronous `HandleSecretSpawns` scope restores temporary eligibility hooks/chance flags on both success and error. The single-selected-object scope passes native trove eligibility without the optional future-pedestal reservation count: already occupied pedestals were removed, and this operation cannot spawn the reserved well/purge siblings. Native creation failures after mutation remain unknown outcomes under the existing recovery journal. A lost acknowledgement retains that record and requires the existing same-process restart interlock; none of these actions are automatically retried.

## Evidence and pending acceptance

The implementation was written from the supported native owners and official bilingual text. `world_catalog.json` owns generated reward identities and native facility names; Trainer-owned action labels use explicit bilingual pairs. Whole-workbench search discovers both those names and the action destinations; fishing and Chaos Gate have workbench-ordered customizable shortcuts.

Authored coverage is `tests/test_hades_world_commands.py` for canonical boundary validation and one-shot/profile separation, `tests/test_hades_world_workflows.py` for native-shaped resource bookkeeping, pickup creation, source/descriptor gating, stale room/door requests, native in-place reroll invalidation, restore, eligible routing, depth-11 forced-pool rejection, potentially forced protection without extra RNG draws, callback restoration on force-query errors, Erebus occupancy with one versus two secret points, pre-creation footprint-query errors, consumed/cancelled Thanatos intent, scoped generation and scope cleanup on native failure, and the affected journey in `tests/test_hades_frontend.py` for bilingual discovery and hero/room-targeted dispatch. Existing recovery tests own the shared unknown-outcome journal behavior.

Executed automation evidence belongs to each exact-source PR; [PROJECT_STATUS.md](../../../PROJECT_STATUS.md) owns operating limits and manual acceptance. Actual rendered rewards, native fishing/catches/turn-in, chamber objects/menus, eligible routes, real door transitions, Thanatos completion and save/load persistence require their own exact-source user-run game evidence. Historical native evidence for other Hades changes does not establish these outcomes.
