# Hades I resources, gathering, rooms and rewards

This is the source-backed capability map for [#572](https://github.com/TeaganRicardo/MacGamingTrainer/issues/572). The supported image is owned by `Backend/games/hades/module.json.supportedBuild`. `world_catalog.json.sourceEvidence` binds the native script and official bilingual text inputs; `Tools/generate_hades_world_catalog.py --content <Content>` reproduces that registry without executing game scripts. Combat and boon effects have their own [map](combat_effects.md); [management parity](management-parity.md) records [#573](https://github.com/TeaganRicardo/MacGamingTrainer/issues/573), with semantic Save Editor completion retained in [#584](https://github.com/TeaganRicardo/MacGamingTrainer/issues/584).

Native chance forcing is scoped to the requested operation. Native eligibility requirements remain authoritative; the UI lists only eligible routes and chamber objects and disables fishing/gate generation when unavailable. A selected reward that fails its native source or descriptor requirements returns the localized unavailable result before mutation.

`RunManager.lua:ChooseNextRoomData` gives its eligible forced pool priority over ordinary eligible rooms. `IsRoomForced` can itself draw `RandomChance` for depth windows and remaining-wing rules. Trainer inspection calls that native owner with the current run, source room, candidate and ordinary-selection arguments, while temporarily treating positive force chances as possible. The exact original callback is restored after success or error. This deliberately protects potentially forced routes; it is not a receipt of an earlier native random selection. Status, disabled inspection and route availability do not redraw force chances, and the ordinary native selector retains its original RNG calls. The fixed depth-11 pre-boss rule follows native `ForceAtBiomeDepthMin/Max`; `ForcedFirstReward` also protects its shop reward.

## One-shot ownership and recovery

World Actions commands are explicit one-shots. The adapter and debugger worker validate the Hero target separately from a runtime room token, exact physical exit token and request ID. The resident owns acknowledged per-door leases and one run-scoped named-occurrence lease. No world-action intent enters preferences, profiles or connect-time replay.

The two ordinary Hades I rows use the same Core-owned picker/action presentation as Hades II: Modify Exit selects a concrete offered exit and an eligible reward/category; Named Encounter selects an available NPC/special strategy. Both controls use an Apply button whose pressed appearance is reconciled from authoritative resident observation. Selecting another exit does not transfer an existing lease; offline controls remain visible but unavailable.

For a reward, Apply updates only the chosen native target and native preview, while capturing the original target, reroll flag and offered-reward entry. Cancel restores the snapshot before that exit is used. For a generic category, Apply creates only a per-door reservation and native preview descriptor; Cancel restores the existing native preview without calling irreversible CreateRoom. On successful native LeaveRoom, the destination is created once. An unused sibling exit's pending reward or category preview is restored before departure bookkeeping. Native force/eligibility and run/hero/source/door/target identity are rechecked.

Named occurrences are one-shot resident state scoped to the current run and hero, with explicit Apply/Cancel and no persistence. A named story/shop room is consumed only after native LeaveRoom commitment; a Thanatos combat encounter is consumed after native RecordEncounter. Changing rooms preserves the request, but an old room object or foreign run cannot borrow it. Native room generation establishes a scoped valid selection context and releases it even on native error. Disable All and run/hero/resident replacement revoke pending requests; a reconnect only observes surviving resident state.

The synchronous `HandleSecretSpawns` scope restores temporary eligibility hooks/chance flags on both success and error. The single-selected-object scope passes native trove eligibility without the optional future-pedestal reservation count: already occupied pedestals were removed, and this operation cannot spawn the reserved well/purge siblings. Native creation failures after mutation remain unknown outcomes under the existing recovery journal. A lost acknowledgement retains that record and requires the existing same-process restart interlock; none of these actions are automatically retried.

## Evidence and pending acceptance

The implementation was written from the supported native owners and official bilingual text. `world_catalog.json` owns generated reward identities, native facility names and each reward's Generate row and section; the generator classifies rewards as the Hades II resident catalog does (Olympian gods and Hermes; Hammer, Pom and room/resource drops; Chaos as a character reward under its native NPC title). Trainer-owned action and section labels use explicit bilingual pairs. Whole-workbench search discovers both those names and the action destinations; fishing, Chaos Gate and the three Generate reward rows have workbench-ordered customizable shortcuts.

Regression coverage includes canonical one-shot command validation, two-row Core picker/action semantics, per-exit reward and route leases, zero-RNG/zero-CreateRoom category Apply/Cancel, native preview restoration, forced/linked route refusal, denied exit use, one-time late native commit, unused sibling reward restoration before departure, stale room/door/reroll denial, independent one-shot encounter consumption, retained cross-room occurrence, stale/foreign encounter rejection, scoped native CreateRoom selection, hero replacement, fishing/Chaos/Erebus and chamber-object behavior. The Hades II owner has separate exact-exit and occurrence suites; both games remain subject to exact-head Linux, module and macOS validation.

Executed automation evidence belongs to each exact-source PR; [PROJECT_STATUS.md](../../../PROJECT_STATUS.md) owns operating limits and manual acceptance. Actual rendered rewards, native fishing/catches/turn-in, chamber objects/menus, eligible routes, real door transitions, Thanatos completion and save/load persistence require their own exact-source user-run game evidence. Historical native evidence for other Hades changes does not establish these outcomes.
